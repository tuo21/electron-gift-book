# 软件激活系统优化实施方案

## 目标

1. 将激活码长度从约 120 字符缩短至 20\~25 字符，提升易用性。
2. 允许部分硬件变更时仍能激活，减少客诉。
3. 增强错误提示的明确性，降低支持成本。
4. 提高密钥安全性（混淆存储，长远过渡到非对称签名）。

***

## 一、短激活码方案

### 1.1 格式设计

- **Payload 字段压缩**：单字母 key
  ```json
  {"m":"381C-7CEE-88","n":"用户","e":null}
  ```
- **签名截断**：取 HMAC-SHA256 的前 6 字节（48 位），碰撞概率约 2.8e-14，足够离线场景。
- **编码**：采用 **Crockford Base32**（字母+数字，去除易混淆字符 I、L、O、U）。
- **激活码格式**：`XXXX-XXXX-XXXX-XXXX-XXXX`（5 组，每组 4 字符，共 20 字符）。

### 1.2 生成器改造 (Node.js)

```javascript
import crypto from 'crypto';
import base32Encode from 'base32-encode'; // 需安装库如 'base32-encode'
import { Buffer } from 'buffer';

const SECRET_KEY = 'GIFT_BOOK_LICENSE_KEY_2026_V1.0';
const SIGN_BYTES = 6;  // 48位签名长度

function generateShortLicense(machineId, name = '用户', exp = null) {
  const payload = { m: machineId, n: name, e: exp };
  const json = JSON.stringify(payload);

  // 1. 对 JSON 进行 HMAC-SHA256
  const hmac = crypto.createHmac('sha256', SECRET_KEY);
  hmac.update(json);
  const fullSign = hmac.digest();

  // 2. 取前6字节签名
  const shortSign = fullSign.subarray(0, SIGN_BYTES);

  // 3. 将 (签名 + JSON) 合并为 Buffer
  const payloadBuffer = Buffer.from(json, 'utf8');
  const combined = Buffer.concat([shortSign, payloadBuffer]);

  // 4. Base32 编码（Crockford，无填充）
  const token = base32Encode(combined, 'Crockford', { padding: false });

  // 5. 格式化：4字符一组，大写
  const grouped = token.match(/.{1,4}/g).join('-').toUpperCase();
  return grouped;
}
```

### 1.3 验证器改造 (Rust)

```rust
use sha2::{Sha256, Digest};
use hmac::{Hmac, Mac};
use data_encoding::BASE32_NOPAD; // Crockford base32
use serde_json::Value;

const SECRET_KEY: &[u8] = b"GIFT_BOOK_LICENSE_KEY_2026_V1.0";
const SIGN_BYTES: usize = 6;

pub fn verify_short_license(short_code: &str) -> Result<LicenseInfo, String> {
    // 1. 清洗输入：去横线、空格，转大写
    let clean = short_code.replace('-', "").replace(' ', "").to_uppercase();

    // 2. Base32 解码
    let combined = BASE32_NOPAD.decode(clean.as_bytes())
        .map_err(|_| "激活码格式错误")?;

    if combined.len() < SIGN_BYTES + 10 {
        // 至少需要签名+最小JSON {"m":"","n":"","e":null}
        return Err("激活码太短".into());
    }

    // 3. 分离签名和payload
    let sign_bytes = &combined[..SIGN_BYTES];
    let payload_bytes = &combined[SIGN_BYTES..];

    // 4. 验证 HMAC
    type HmacSha256 = Hmac<Sha256>;
    let mut mac = HmacSha256::new_from_slice(SECRET_KEY)
        .map_err(|_| "密钥初始化失败")?;
    mac.update(payload_bytes);
    let expected_sign = mac.finalize().into_bytes();

    if !constant_time_eq(&sign_bytes, &expected_sign[..SIGN_BYTES]) {
        return Err("激活码无效".into());
    }

    // 5. 解析JSON
    let payload: LicenseInfo = serde_json::from_slice(payload_bytes)
        .map_err(|_| "数据损坏".into())?;

    // 6. 机器码比对（统一小写、去横线）
    let current_mid = get_machine_id()?;
    let stored_mid = payload.mid.replace('-', "").replace(' ', "").to_lowercase();
    let current_mid_clean = current_mid.replace('-', "").replace(' ', "").to_lowercase();

    if stored_mid != current_mid_clean {
        return Err("机器码不匹配".into());
    }

    // 7. 可选的过期检查
    if let Some(exp) = payload.exp {
        let now = std::time::SystemTime::now()
            .duration_since(std::time::UNIX_EPOCH)
            .unwrap()
            .as_secs();
        if now > exp {
            return Err("激活码已过期".into());
        }
    }

    Ok(payload)
}
```

> **注意**：`LicenseInfo` 结构体字段需改为 `m`, `n`, `e`，或添加反序列化别名：
>
> ```rust
> #[derive(Deserialize)]
> struct LicenseInfo {
>     #[serde(alias = "m")]
>     mid: String,
>     #[serde(alias = "n")]
>     name: String,
>     #[serde(alias = "e")]
>     exp: Option<u64>,
> }
> ```

### 1.4 验证步骤

1. 用生成脚本生成短码：`generateShortLicense("381C-7CEE-88", "用户")`。
2. 将短码输入软件激活，应成功。
3. 故意修改短码中一个字符，应报“激活码无效”。
4. 换一台机器码不同的电脑测试，应报“机器码不匹配”。

### 2.2 模糊比对逻辑

激活码中存储预期的指纹列表（或仅存储各组件哈希）。验证时允许部分匹配。

- **存储方式**：在 JSON 中增加 `f` 字段，值为各组件哈希数组的前8位十六进制。
  ```json
  {"m":"381C-7CEE-88","n":"用户","e":null,"f":["a3f2","1b44","e99d"]}
  ```
- **匹配规则**：至少 4/5 项匹配即认定同一机器。

```rust
fn fuzzy_match(stored_hashes: &[String], current: &MachineFingerprint) -> bool {
    let current_hashes = vec![
        hash_component(&current.board_id),
        hash_component(&current.bios_version),
        hash_component(&current.cpu_model),
        hash_component(&current.computer_name),
        hash_component(&current.disk_serial),
    ];
    let mut matches = 0;
    for ch in &current_hashes {
        if stored_hashes.contains(ch) {
            matches += 1;
        }
    }
    matches >= 4 && stored_hashes.len() >= 4
}

fn hash_component(s: &str) -> String {
    let digest = Sha256::digest(s.as_bytes());
    hex::encode(&digest[..2]) // 取前2字节作为短哈希
}
```

### 2.3 生成器更新

```javascript
function generateFingerprintHashes(payload) {
  const components = [payload.boardId, payload.bios, payload.cpu, payload.computer, payload.disk];
  return components.map(c => crypto.createHash('sha256').update(c).digest('hex').substring(0,4));
}
// 在生成 short license 时添加 "f": hashes
```

### 2.4 验证步骤

1. 在正常环境下激活，记录当前指纹。
2. 修改计算机名，再次激活：应通过（其他4项匹配）。
3. 同时修改计算机名和拔掉外置硬盘（假设指纹5项中变化2项），应失败，除非匹配阈值放宽到3。
4. 阈值建议配置化，方便后期调整。

## 三、错误提示细化

### 3.1 增加错误枚举

```rust
enum LicenseError {
    InvalidFormat,
    InvalidSignature,
    MachineMismatch { current_mid: String, stored_mid: String },
    Expired,
    CorruptedData,
}
```

### 3.2 前端展示友好信息

- `InvalidFormat` → “激活码格式不正确，请检查是否复制完整。”
- `InvalidSignature` → “激活码已失效或被篡改。”
- `MachineMismatch` → “当前机器码 XXXX-XXXX-XX 与激活码绑定的 YYYY-YYYY-YY 不一致。如更换了少量硬件，请尝试重新激活或联系支持。”
- `Expired` → “激活码已过期，请续费。”

### 3.3 调试信息

在 debug 模式下，将 `current_mid` 和 `stored_mid` 输出到日志和界面（可点击复制），便于用户反馈。

## 四、密钥安全增强（可选，进阶）

### 4.1 密钥混淆存储

Rust 中密码不以明文出现，改为通过 XOR 与一个编译期常量拼接：

```rust
const KEY_PART1: &[u8] = b"GIFT_BO";
const KEY_PART2: &[u8] = b"OK_LICE";
// 运行时拼装
let secret = [KEY_PART1, KEY_PART2].concat();
```

（仅供临时提升逆向门槛，非彻底方案）

### 4.2 非对称签名过渡

- 生成器持有 Ed25519 私钥，签发签名。
- 客户端只硬编码公钥。
- 激活码格式改为：`payload + 短签名（64字节，可用Base32编码）`。
- 短签名用法：
  ```rust
  use ed25519_dalek::{Verifier, PublicKey, Signature};
  // 验证
  public_key.verify(payload_bytes, &signature)?;
  ```
- **验证步骤**：
  1. 用 Node 脚本（使用 `tweetnacl` 或 `ed25519`）生成密钥对，私钥安全存储。
  2. 签发激活码，客户端验证通过。
  3. 尝试用另一对密钥签发，应失败。

## 五、测试用例清单

| 编号 | 测试场景              | 预期结果          |
| :- | :---------------- | :------------ |
| 1  | 正常激活（短码）          | 激活成功          |
| 2  | 短码中字符修改           | 提示“激活码无效”     |
| 3  | 机器码完全一致但大小写混用     | 激活成功（小写统一）    |
| 4  | 修改计算机名，其他硬件不变     | 激活成功（模糊匹配）    |
| 5  | 修改计算机名+磁盘序列号+主板ID | 激活失败（低于阈值）    |
| 6  | 激活码过期             | 提示“已过期”       |
| 7  | 输入包含多余空格和横线       | 自动清洗后激活成功     |
| 8  | 旧版长激活码仍可激活        | 向后兼容（保留旧验证路径） |

## 六、实施路线图

1. **第一阶段**：完成短码改造（生成器+验证器），保留旧版验证路径作为兼容。
2. **第二阶段**：实现模糊匹配，配合更新后的指纹收集，灰度发布。
3. **第三阶段**：改进错误提示，统一错误处理接口。
4. **第四阶段**：评估非对称签名，待稳定后切换。

每个阶段完成后，需通过上述测试用例验证，并保留旧版激活码解析能力至少2个大版本。
